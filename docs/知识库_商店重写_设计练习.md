## 二、MVC 在你这个场景具体是什么

MVC 最容易搞砸的地方是：三层都变成了"什么都干一点"。用商店举例，边界是这样：

```
┌──────────────────────────────────────────────────┐
│  Model —— 数据 + 规则，不认识任何 Unity UI         │
│    · ShopData / ShopItemData   卖什么、多少钱      │
│    · PlayerWallet              玩家有多少钱        │
│    · Inventory                 玩家已经有什么       │
│    · 纯逻辑：买得起吗 / 扣钱 / 发货                 │
├──────────────────────────────────────────────────┤
│  Controller —— 流程编排                            │
│    · 收到"要买第 3 个商品"                          │
│    · 问 Model：买得起吗                             │
│    · 让 Model：扣钱、发货                           │
│    · 发出结果：成功 / 失败（什么原因）               │
├──────────────────────────────────────────────────┤
│  View —— 只显示，不做判断                          │
│    · 根据数据创建商品格子                           │
│    · 显示金币数                                     │
│    · 把"点击"转发出去，自己不处理                    │
│    · 根据状态改颜色 / 灰掉                           │
└──────────────────────────────────────────────────┘
```

### 一条自查判据（很好用）

> **类里出现 `transform.Find` / `Image` / `TextMeshProUGUI` → 它是 View。**
> **类里出现 `if (金币 >= 价格)` → 它是 Model 或 Controller。**
> **一个类两样都有 → 它已经开始变成上帝类了。**

## 三、你必须自己拍板的五个问题

这些没有标准答案，**选哪个都行，但你要说得出为什么**。

### 1. "发货"怎么写？

- **A：枚举 + switch** —— 简单直接，但每加一种商品类型就要加一个分支
- **B：每个商品自己知道怎么发** —— 加类型不用改旧代码，但类会变多，新手容易绕晕

> 提示：你现在有几种商品？未来半年可能加几种？**为"可能加"付出的复杂度，值不值？**

### 2. 事件中心用在哪几条边界上？

- 哪些调用应该**直接调方法**
- 哪些应该**发事件广播**

> 提示：**事件中心是"跨模块的广播"，不是"类之间的电话线"。** 同一个模块内部绕事件中心，流程会变得查无可查 —— 出 bug 时你根本不知道谁触发的。

### 3. 买不起的时候，UI 怎么表现？

- 按钮灰掉，点不动
- 按钮能点，点了弹"金币不足"
- 两个都要

> 提示：想一下玩家体验 —— 灰掉的按钮，玩家知道差多少钱吗？

### 4. 商品能不能重复买？

- 药水能买很多瓶
- 钥匙只有一把，买过就不该再出现

> 提示：**这个差异该由谁表达？** 商品数据里加个字段？还是买过就从列表里去掉？两种做法的后果不一样。

### 5. View 怎么知道该刷新？

- **拉**：Controller 处理完，直接调 `view.Refresh()`
- **推**：Controller 发事件，View 订阅事件自己刷新

> 提示：哪种更容易调试？哪种在模块多起来之后更省事？

## 四、写代码的顺序（这个顺序很重要）

```
1. Model       ← 先写。纯 C# 类，别继承 MonoBehaviour
2. Controller  ← 再写。此时可以完全没有 UI，用 Debug.Log 验证流程
3. View        ← 最后写。只做显示 + 转发点击
```

### ⚠️ 绝对不要从 UI 开始写

**从 UI 开始写，逻辑会全部渗进 UI 类里** —— 因为写 UI 的时候手边就有数据，最省事的做法就是"顺手在这儿判断一下"。等你反应过来，`ShopPanel` 已经八百行，什么都在里面。

**那正是你现在想推翻的那个东西的成因。**

从 Model 开始写，你被迫先想清楚"数据长什么样、规则是什么"，UI 最后只是把已有的东西画出来。

## 反馈 1：你漏了"发货"

草案里控制层负责"货币交易"。但买东西**不只是交易**：

```
点击 → 校验（钱够吗）→ 扣钱 → 【发货】→ 更新 UI
                                   ↑
                            这一步你没写
```

**扣完钱，那个东西怎么到玩家身上？**

| 买什么 | "到身上"是什么 |
|---|---|
| 药水 | 回血 |
| 钥匙 | 让玩家有资格开某扇门 |
| （以后）武器 | 换装备 |

**这三种"到身上"的方式完全不一样。这才是商店系统真正难的地方，也是最该想清楚的地方。**

要回答的：
- "发货"写在哪个类里？
- 谁来判断"这是药水，所以回血"？
- 加一种新商品，要改几个文件？

## 卡住的时候用这个方法

> **把"点击购买"这一秒内发生的事，按时间顺序写成流水账。**
> 每行写"**谁**做了**什么**"，用大白话，不管类。
>
> 例：
> 1. 玩家点了第 3 个格子
> 2. 面板告诉控制器：第 3 个被点了
> 3. 控制器去问：这个多少钱？玩家有多少钱？
> 4. 钱不够 → 告诉面板"买不起"
> 5. 钱够 → 扣钱

## 反馈 5：先把"买"和"用"分开

你说"物品数目直接 +，感觉显然不太对"。你的直觉对，但**不对的地方可能不是你想的那个**。

如果是"多一瓶"，那**"买"这个动作对所有物品都是一样的：数量 +1**。
真正不同的是"**用**"的时候 —— 喝药水回血、用钥匙开门。

> ⚠️ **更正我上一轮的说法**：我写的"买药水 → 要回血"是简化过头了，可能误导了你。
> 按你项目的实际设计，**买了是进背包，喝的时候才回血**。

**所以要回答的是**：
- 你现在的商品（药水、钥匙），"发货"能不能统一成"数量 +1"？
- 如果能 → 发货流程就很简单
- 如果不能 → 是哪种不能？那种特殊在哪？

## 反馈 6：你的广播方案有个洞

你说"控制层处理完购买后发送广播，表现层收到广播后修改 UI"。

> **如果打怪掉了 50 金币，金币 UI 怎么更新？**

- 金币的"数值变了"

# 附录：现状盘点（重要 —— 决定你的工作量）

## 已经存在的东西（不用你写）

| 你需要的能力 | 现成的东西 | 它会自己发事件吗 |
|---|---|---|
| 扣钱 | `PlayerWallet` | ✅ `CoinChange` |
| 加消耗品 | `PlayerInventory.AddItem(item, count)` | ✅ `InventoryChange` |
| **加武器** | **`PlayerCombat.AddWeapon(weapon)`** | ✅ `WeaponChange` |
| 商品配置 | `ShopItemData`（SO） | — |
| 武器数据 | `WeaponData`（SO） | — |
| 事件总线 | `EventCenter` | — |

`AddWeapon` 的注释写的就是"**商店购买武器入库（去重）**"，而且里面自带 `weaponInventory.Contains(weapon)` 检查。

## 所以：商店一个事件都不用自己发

**三个事件全都由"数据的主人"发出：**

| 变化 | 谁发 |
|---|---|
| 钱变了 | `PlayerWallet` |
| 消耗品变了 | `PlayerInventory` |
| 武器变了 | `PlayerCombat` |

商店只负责**调用**这些方法。**这正好印证了"谁变了谁发事件"。**

## ⚠️ 你即将撞上的一个坑：扣钱和发货的顺序

看 `AddWeapon` 的行为：

if (weaponInventory.Contains(weapon))

**玩家白花一笔钱。这是你重写时必须解决的第一个真问题。**
