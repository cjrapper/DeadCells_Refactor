# 商店系统 · 施工大纲

> 最后更新：2026-10-19

> **目标**：跑通一次完整的购买。
> **范围**：消耗品 + 钥匙。**武器不在这一版**（写完再数改动量，那是扩展性自测）。
> **不动**：背包、地图拾取。

---

## 一、这个商店要负责什么

四件事，就这四件：

1. 打开面板 → 显示所有商品（图标 / 名字 / 价格）
2. 显示玩家当前金币
3. 点商品 → 买得起就扣钱发货，买不起给反馈
4. **金币变了（不管是买还是捡）→ 显示跟着变**

> **第 4 条要单独想**：它不属于"购买流程"，它是"金币显示"自己的职责。
> 分开了，你就不会把"刷新金币"这段代码塞进购买逻辑里 —— 塞进去的话，捡金币时 UI 就不刷新了。

---

## 二、需要哪些东西

### 数据

| 东西 | 现状 | 你要做的 |
|---|---|---|
| `ShopData` | 商店配置：名字 + 商品列表 | 检查够不够用 |
| `ShopItemData` | 单个商品：类型 / 价格 / 效果 | **很可能要补 icon 和名字字段** |
| `PlayerWallet` | `Coins` / `AddCoins` / `TrySpend` | **自己重写一遍（接口不变）** |

### 逻辑（你写）

| 东西 | 一句话职责 |
|---|---|
| 购买流程 | 校验 → 扣钱 → 发货 → 反馈 |

### 表现（你写）

| 东西 | 一句话职责 |
|---|---|
| 商品格子 | 显示一个商品，把点击转发出去，自己不处理 |
| 商店面板 | 创建所有格子、显示金币、订阅事件刷新 |

## 三、一次购买，从头到尾

```
1. 玩家点了第 N 个商品格子
2. 格子把"第 N 个被点了"告诉面板
3. 面板问钱包：这个价钱扣得掉吗？
   ├─ 扣不掉 → 给"买不起"的反馈 → 结束，什么都不用撤销
   └─ 扣掉了 → 钱已经少了，继续
4. 发货：把物品加进背包
5. 钱包广播 CoinChange → 金币显示自动刷新
6. （背包广播 InventoryChange，以后有背包 UI 它自己会刷新）
7. 结束
```

**关键在顺序**：先扣钱（自带校验），成功了才发货。

**这样不存在"扣了但发不出"的中间状态，所以不需要回滚。**

> 回滚是"先做后补救"，校验是"先想清楚再做"。
> **能靠校验解决，就别引入回滚** —— 回滚代码写错，会出现"钱退了但东西还在"这种更难查的 bug。

## 四、三个你自己拍板的决定

### 决定 1｜分几个类？

- 一个类全干（面板 + 流程）
- 分成"显示"和"流程"两个

各有代价。**选一个，说得出为什么就行。**

### 决定 2｜买不起时怎么反馈？

- 按钮灰掉（点不动）
- 能点，点了提示"金币不足"
- 两个都要

> 想一下：灰掉的按钮，玩家知道差多少钱吗？

### 决定 3｜"金币不足"提示放哪？

- `Debug.Log` —— 最省，但只有你在编辑器里看得到
- UI 上的文字 —— 玩家能看到，但要加一个文字控件

## 五、开发顺序：从底层往上，逐个换成自己写的

### 为什么不用原来的顺序

原计划是"接口不变，只换实现"。那对**生产项目**是对的 —— 外面的人不受影响。

但你的目标是**长进**。`PlayerWallet` / `PlayerInventory` / `ShopPanel` 都不是你写的，在它们上面再盖一层，等于**在别人的地面上盖房子**，地板一动你就塌。

### 先分清两种"不是我写的"

| 类型 | 例子 | 怎么办 |
|---|---|---|
| **项目里的业务代码**（AI 帮你敲的） | `PlayerWallet`、`PlayerInventory`、`ShopPanel` | **重写** |
| **第三方依赖** | xLua、Unity、TMP | **不重写**，会用接口就行 |

没人会去重写 Unity。判断标准是：**这段代码是不是"你的业务"**。

### 顺序：从被依赖的，写到依赖别人的

```
PlayerWallet      ← 谁都不依赖，最小，先写
      ↓
PlayerInventory   ← 依赖钱包（买完要扣钱）
      ↓
ShopItemData / ShopData ← 纯数据，顺手自己定字段
      ↓
ShopPanel         ← 依赖上面所有，最后写
```

**每一步都是「这个模块 + 它的调用方」一起换，跑通再走下一步。**
不是一次性推倒，是逐个换血 —— 任何时刻游戏都是能跑的。

---

### 第 1 步：自己写 PlayerWallet

**规模**：大概 30 行。整个计划里最小、最独立的一块。

**它要支持什么？从调用方反推**（这是真本事，不是背接口）：

| 谁在用 | 它需要什么 |
|---|---|
| `CoinPickup`（地图捡金币） | 加钱 |
| `UIManager`（HUD 显示） | 读当前钱数 + 变化时被通知 |
| 商店（花钱） | 扣钱，**并且知道成没成功** |

> "并且知道成没成功"这一条，决定了扣钱方法**必须有返回值**。
> `TrySpend` 返回 `bool` 不是随手设计的，是被调用方逼出来的。

**还要自己想到的**：
- 钱不能扣成负数
- 钱一变就要广播 `CoinChange`，否则 HUD 不更新
- **捡金币和花钱都要广播**（不只是花钱）

**✅ 验证**：进游戏捡金币 → HUD 数字会涨。一条不通就别往下走。

---

### 第 2 步：自己写 PlayerInventory

**规模**：比钱包大，大概 80~100 行。

**它要支持什么**：

| 谁在用 | 它需要什么 |
|---|---|
| 商店（发货） | 加一件物品 |
| 背包面板（使用） | 用掉一件、查还剩几件 |
| 商店面板（显示已拥有） | 查有多少件 |

**要自己想到的**：
- 同一件物品买两次，**叠数量**还是**占两格**？
- 用掉一件后数量归零，这个槽位删不删？
- "满血不能喝药"这种规则放在这儿合适吗？

**✅ 验证**：买一瓶药水 → 背包里出现；喝掉 → 数量减一。

---

### 第 3 步：自己定数据字段

`ShopItemData` / `ShopData` 是**纯数据类**，没有逻辑，重写成本很低。

但值得自己过一遍：**商店到底需要知道哪些字段？**
- 名字、图标、价格 —— 要
- 类型（武器 / 消耗品）—— 要
- 武器的伤害冷却 —— 那在 `WeaponData` 里，这里只存引用

**✅ 验证**：Inspector 里能配出一个完整的商品。

---

### 第 4 步：自己写 ShopPanel

前三步是地基，到这里才是你最初想写的那个。

**分两小步，别一次写完：**

**4a｜只显示，不买**
- 读 `ShopData` → 生成格子 → 显示图标 / 名字 / 价格
- **这一版不要写点击**

✅ 验证：打开面板能看到所有商品，排布对

**4b｜接上购买**
- 点击 → 调钱包扣钱 → 调背包发货 → 订阅事件刷新

✅ 验证：点一下，金币少了，背包里多了一件

---

### 第 5 步：边界和反馈
- 钱不够
- 金币显示会不会跟着刷新
- 连点两次会怎样

**✅ 验证**：钱不够时点击，金币不变且有反馈

### 第 6 步（自测）：加武器
- 往商店里加一个武器商品，把流程接上
- **数一下改了几个文件**

> **这就是你的扩展性得分。**
> 改 1~2 个文件 = 设计不错；改 4 个以上 = 哪里耦合了，回头看看。

---

## 六、写代码时随身带三条

1. **🔍 自查判据**
   类里出现 `Image` / `Text` / `transform.Find` → **View**；
   出现 `if (钱 >= 价)` → **逻辑**。
   **两样都有 = 上帝类开始长了。**

2. **不许问我要代码。** 可以问"这个 API 怎么用"。

3. **每步跑通再往下。** 跳步的代价是最后一起 debug，那时候你分不清是谁的问题。

---

## 七、卡住的时候

- **想不出某个类该有哪些方法** → 写流水账（第三节那种），把主语相同的行圈在一起
- **不确定该不该发事件** → 问自己"除了我，还有谁关心这件事？"没有就别发
- **不确定某段逻辑该放哪** → 问自己"如果把它删了，哪个类会缺东西？"
