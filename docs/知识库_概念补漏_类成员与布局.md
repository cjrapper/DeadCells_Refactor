## 一、类的四种成员：字段、属性、方法、参数

写一个类的时候，你只可能在写这四样：

| 成员 | 长什么样 | 作用 | 存在多久 |
|---|---|---|---|
| **字段** field | `private PlayerWallet wallet;` | **存数据** | 跟对象一样长 |
| **属性** property | `public int Coins { get; private set; }` | 带访问控制的字段 | 跟对象一样长 |
| **方法** method | `public void TryBuyItem(...) { }` | **行为** | 调用时执行 |
| **参数** parameter | 方法括号里声明的 | **方法的输入** | 只在方法体内 |

### 关键区别：字段 vs 参数

```csharp
private ShopData currentShop;                        // ← 字段：整个类都能用

public void Open(ShopData shop)                      // ← 参数：只有这个方法内能用
{
    currentShop = shop;                              // 把参数存进字段
}
```

**为什么要存？** 因为参数出了方法就没了，字段一直在。

> **这就是你之前那个 bug 的根源**：`Refresh` 里读 `currentShop`，但 `Open` 收了 `shop` 参数却没存进字段 → 永远是 null。

### ⚠️ 参数会"遮蔽"同名字段

```csharp
private PlayerWallet wallet;                                    // 字段
public void TryBuyItem(PlayerWallet wallet, ...)                // 参数也叫 wallet
{
    wallet.Coins;    // ← 这里指的是【参数】，字段被遮住了
}
```

**编译器不报错，但你会误以为在改字段。**

**解决**：既然有字段了，方法就别再收这个参数。**字段就是"这个类的记忆"，不需要每次重新传。**

## 二、引用类型必须赋值吗？—— 看它在哪

**"必须赋值才能用"是【局部变量】的规则，不是【字段】的规则。**

| 位置 | 默认值 | 不赋值能用吗 |
|---|---|---|
| **字段**（类里） | `null`（引用类型）/ `0`（int）/ `false`（bool） | ✅ **能**，默认 null |
| **局部变量**（方法里） | **没有默认值** | ❌ **编译错误** |
| **数组元素** | 同字段，有默认值 | ✅ |

```csharp
class A
{
    private PlayerWallet wallet;    // ✅ 合法，默认 null

    void Foo()
    {
        PlayerWallet w;             // ✅ 声明合法
        w.Coins;                    // ❌ 编译错误：使用了未赋值的局部变量
    }
}
```

### 关于 `null`

`null` = "**这个引用没指向任何对象**"。它不是 C++ 的野指针 —— C# 是类型安全的，`null` 只对引用类型有效，而且访问 null 会抛 `NullReferenceException`（**明确报错**，不会读脏内存）。

**所以 `private PlayerWallet wallet;` 是合法的，但在赋值之前它就是 `null`。**
在 `Open()` 里 `GetComponent` 拿到之后才真正有值。

## 三、`static` / `readonly` / `const`

### 3.1 `static` = 属于"类"，不属于"某个对象"

```csharp
public class PlayerWallet
{
    public int Coins;                 // 实例字段
    public static int TotalCoinsEver; // 静态字段
}
```

| | 每个对象一份？ | 怎么访问 |
|---|---|---|
| `Coins`（实例） | ✅ **每个对象各有一份** | `walletA.Coins`、`walletB.Coins` |
| `TotalCoinsEver`（静态） | ❌ **整个类共用一份** | `PlayerWallet.TotalCoinsEver`（**用类名，不用对象**） |

**"属于类型不属于实例" = 不依附于任何具体对象，直接挂在"类"这个蓝图上。**

**什么时候用 static？**
- **单例**：`public static ShopPanel Instance;`
- **全局共享数据**：计数器、配置缓存
- **工具方法**：`UIFactory.CreateText(...)` —— 不需要 new 一个工厂对象就能用

> **危险**：静态字段活得和"程序"一样久，**不会随场景卸载**。
> 单例忘了清（比如场景重载时旧实例还挂着），就会出现你项目里踩过的 `this lua env had disposed` 那种 bug。

### 3.2 `readonly` = 只能在"声明时"或"构造函数里"赋值

```csharp
private readonly List<Button> buyButtons = new();   // ✅ 声明时赋值

PlayerWallet()
{
    buyButtons = new List<Button>();                // ✅ 构造函数里赋值也行
}

void Foo()
{
    buyButtons = new List<Button>();                // ❌ 编译错误
}
```

### ⚠️ 大坑：`readonly` 锁的是"引用"，不是"内容"

```csharp
buyButtons = new List<Button>();   // ❌ 不能换掉这个列表
buyButtons.Add(btn);               // ✅ 可以！
buyButtons.Clear();                // ✅ 也可以！
```

**`readonly` 的意思是"这个把手不能换"，不是"手里的东西不能动"。**

### 3.3 `const` = 编译期常量

**什么是"编译期常量"？** —— 编译器在打包时就能确定值，并把它**直接写死**到每一处使用的地方。

```csharp
const int MaxHP = 100;                // ✅ 数字
const string Name = "Player";         // ✅ 字符串
const bool Debug = true;              // ✅ bool
const float Speed = 1.5f;             // ✅ 浮点数

const int Double = MaxHP * 2;         // ✅ 编译期能算出来

const List<int> L = new();            // ❌ 对象不能 const
const DateTime D = ...;               // ❌ 结构体/对象不能 const
```

**为什么 `List` 不能 const？** 因为 `const` 要求"打包时就知道值"，而 `new List<int>()` 要**运行时**才创建出来。

**所以：对象只能用 `static readonly` 或 `readonly`，不能用 `const`。**

### 3.4 三者对照

| 关键字 | 管什么 | 能用于对象吗 |
|---|---|---|
| `private` / `public` | **谁能访问** | ✅ |
| `static` | **属于类还是属于对象** | ✅ |
| `readonly` | **能不能重新赋值**（声明后不行） | ✅ |
| `const` | **编译期常量**（写死） | ❌ 只能基本类型/string |

**四个维度互不干扰。** `private static readonly` 三个一起用完全合法。

## 四、UGUI 行内布局：三个元素怎么摆

**你的疑问**："左区有两个元素，那不就得算比例了吗？"

**不一定。有三种策略，按"元素数量会不会变"来选：**

### 策略 A：固定位置（元素少、不会变）

```
名字   anchoredPosition.x = 16,  sizeDelta.x = 200
限购   anchoredPosition.x = 230, sizeDelta.x = 100
价格   anchoredPosition.x = 340, sizeDelta.x = 80
按钮   锚右，anchoredPosition.x = -16
```

**特点**：全部锚左侧 / 右侧，位置写死。
**加元素**：要改后面所有元素的 x。
**适合**：就这几个，永远不变。

### 策略 B：分区（比例分割）

```
左区    anchorMin = (0, 0), anchorMax = (0.65, 1)   ← 占 65% 宽度
右区    anchorMin = (0.65, 0), anchorMax = (1, 1)   ← 占 35%
```

**特点**：**这才是"按比例"** —— 父级变宽，两个区按比例一起变。
**加元素**：要重新分配百分比。
**适合**：元素分组清晰、数量固定。

### 策略 C：Horizontal Layout Group（元素数量会变）

- 父物体挂 `HorizontalLayoutGroup`，设 `spacing`、`padding`、`childAlignment`
- 子物体不用管位置，**按添加顺序自动从左往右排**
- 配合 `LayoutElement` 指定各自的 `preferredWidth`

**特点**：**加减元素完全不用改代码。**
**适合**：列表、动态生成的行。

### 怎么选

| 你的情况 | 选 |
|---|---|
| 行内就 3 个固定元素 | **A**（最省事） |
| 要按比例拉伸、分组明确 | **B** |
| 元素数量会变（比如以后加"限购""库存"） | **C** |

> **"比例"和"锚点"不是一回事**：
> - **锚点**表达的是"相对父级哪个位置"
> - **比例**是锚点的一种特殊用法（min 和 max 分开，形成拉伸）

### 行容器到底是什么

**是一个"坐标系 + 移动单位"。**

- 它不是"按比例摆放"的 —— 子元素默认按**自己的锚点**定位
- 它的真正价值：**让这一行的所有东西能被整体移动**（改行容器的 y，里面全跟着走）

## 五、关于"理解到什么程度"

**你的原话**：
> "我怕我不理解的话，一切都停留在表面，很虚浮。"

### 这个担心是对的，但要换个框架

**不是"理解 vs 不理解"，而是"什么时候理解什么"。**

| 对某个模块的用法 | 什么时候需要理解内部 |
|---|---|
| 只调 1~2 个方法 | **不需要**（比如 `List.Add`） |
| 经常用、改过、踩过它的坑 | **必须懂** |
| 你打算自己重写它 | **必须懂**，但要单独安排一轮 |

### 你现在的具体情况

`PlayerInventory` —— **你不是"不该理解"，而是"时机不对"。**

你已经说了要重写它。所以：
- ✅ **迟早要彻底懂**
- ❌ **但不是在写商店的时候顺便读**

**顺序应该是**：
```
商店写通（只需要知道 PlayerInventory 有 AddItem(物品, 数量)）
   ↓
专门花一轮重写 PlayerInventory（那时候会真正懂）
   ↓
回头把商店改成用新的
```

**两件事混在一起做，节奏会乱，而且哪件都做不深。**

### 区分"用"和"懂"

| | 要求 |
|---|---|
| **用** | 知道方法名、参数、返回值、什么情况下会失败 |
| **懂** | 知道它内部怎么实现、为什么这么设计 |

**前者是必须的，后者是按需的。**

> 没人"懂" `List<T>` 的内部实现也照样天天用它。
> **真正的"虚浮"不是"不懂内部"，而是"以为自己懂"。**
> 你现在知道自己不懂 —— **这是好事**，说明判断力还在。

# 六、集合查找：`Find` / lambda / `var`

## 6.1 `List.Find` 是干什么的

**在一组东西里，找出"第一个符合条件的"那个。**

```csharp
var slot = slots.Find(s => s.itemData == item);
```

拆开读：

```
slots . Find (  s   =>   s.itemData == item  )
  ↑      ↑     ↑            ↑
 列表   方法  遍历到的      这一项装的是不是我要找的那个？
              每一项
```

**它做的事：**
1. 从头到尾遍历 `slots`
2. 对**每一项**执行一次 `s => s.itemData == item`
3. 返回**第一个判断为 true 的那一项**
4. 全都不符合 → 返回 **`null`**

### 等价的写法（手写循环）

```csharp
InventorySlot slot = null;
foreach (var s in slots)
{
    if (s.itemData == item)
    {
        slot = s;
        break;          // 找到就停，后面的不看
    }
}
```

**`Find` 就是把这段循环压成一行。** 你写的是同一件事。

---

## 6.2 lambda 表达式 `s => ...`

**lambda = "一个没名字的小函数"，用来当参数传给别的函数。**

| 写法 | 参数个数 | 用在哪 |
|---|---|---|
| `() => DoSomething()` | 0 | 按钮点击回调 |
| `s => s.itemData == item` | 1 | `Find` / `Where` |
| `(a, b) => a + b` | 2 | 排序比较 |

**`s` 是你自己起的名字**（形参），代表"当前这一项"。叫 `x`、`slot`、`it` 都行：

```csharp
slots.Find(x => x.itemData == item)     // 完全等价
```

**`=>` 左边是参数，右边是返回值（或语句）。** 多语句要加花括号：

```csharp
() =>
{
    Debug.Log("clicked");
    TryBuyItem(item);
}
```

---

## 6.3 `var` 是类型推断

```csharp
var slot = slots.Find(...);     // 编译器推导出 InventorySlot
```

**等价于**：

```csharp
InventorySlot slot = slots.Find(...);
```

**`var` 不是"没有类型"**，是"你懒得写，让编译器看着办"。推导出来之后就固定了。

> **什么时候别用 `var`？** 当右边看不出类型时（比如 `var x = GetData();`），写明确类型更好读。

---

## 6.4 常用集合查找 API 对照

| 想干什么 | 用什么 | 返回什么 |
|---|---|---|
| 找第一个符合条件的**元素** | `List.Find(pred)` | 元素 **或 null** |
| 找第一个符合条件的**下标** | `List.FindIndex(pred)` | `int`（没有是 **-1**） |
| 有没有符合条件的存在 | `List.Exists(pred)` | `bool` |
| 筛出所有符合的 | `List.FindAll(pred)` | **新 List**（可能是空的） |
| 有没有这个元素 | `List.Contains(x)` | `bool` |
| 按条件排序 | `List.Sort(cmp)` | `void`（原地排） |
| **字典**按 key 查 | `Dictionary.TryGetValue(k, out v)` | `bool` |

> **⚠️ 三种"找不到"的表达不一样：**
> - `Find` → `null`
> - `FindIndex` → `-1`
> - `TryGetValue` → `false`
>
> **记混了就会写出 `if (index == null)` 这种错。**

---

## 6.5 为什么这里能直接 `s.itemData == item`

因为 `ShopItemData` 是 **ScriptableObject 资产** —— 全项目只有**一份** `HealthPotion.asset`，所有引用都指向它。

**所以引用相等 = 同一种物品。**

> 如果物品是普通 `class`，你 `new` 两个一样的药水，引用就不相等了，得自己写 `Equals`。
> **SO 的"唯一实例"特性让判断变简单了。**

## 6.6 四个坑

| 坑 | 后果 |
|---|---|
| `Find` 返回 null，忘了判空就 `.count` | **NullReferenceException** |
| 在 `foreach` 里 `Add` / `Remove` 集合 | 抛异常（迭代器失效） |
| 把 `slots`（列表）和 `slot`（一格）搞混 | `slots.item` 编译不过 |
| **`Count`（列表有几个元素）当成"物品数量"** | **逻辑错但不报错**，最隐蔽 |

**最后一条最隐蔽**：`List.Count` 是"列表里有几格"，不是"某种物品有几个"。物品数量在 `slot.count`（类里的字段）。

## 6.7 更危险的坑：方法互相调用 → 无限递归

```csharp
TrySpendItem() { ...; UseItem(); }        // A 调 B
UseItem()      { ...; TrySpendItem(); }   // B 又调 A
```

```
A → B → A → B → ...   → StackOverflowException
```

**编译不报错，运行时直接崩。**

> **规则：只要写出"A 调 B、B 又调 A"的关系，立刻停下来检查。**
>
> 正确做法是**单向**：外层方法调内层，内层不许回调外层。
>
> ```
> UseItem → RemoveItem     ✅ 单向
> UseItem ↔ TrySpendItem   ❌ 环
> ```

## 6.8 改完一定要查"谁在用"

**你改了 `PlayerInventory` 的三个地方，`InventoryPanel` 就全红了：**

| 你改的 | 旧代码还在用 |
|---|---|
| `slots` 变 private | `playerInventory.slots.Count` |
| `InventorySlot` 移进类里 | `foreach (InventorySlot slot in ...)` |
| `slot.item` → `slot.itemData` | `slot.item.itemName` |

> **规律**：**改一个类的成员（名字/访问级别/结构），一定要搜索整个项目的引用。**
> Unity Console 会告诉你，但**你得先让它编译**才看得到。
>
> 快速搜法：VSCode `Ctrl+Shift+F` 搜符号名。
