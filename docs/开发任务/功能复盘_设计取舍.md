# 功能复盘（一）：设计取舍 —— 为什么这么拆

> 最后更新：2026-09-10

> 配套阅读：`功能复盘_配置手册.md`（每个系统具体怎么配）
>
> 这份文档解决的是你问的那个问题：**"我不知道是定一个可售卖接口，还是用枚举，还是别的组合"**。
> 答案不是"哪个更高级"，而是"**在当前规模下哪个成本最低，以及什么时候该换**"。

---

## 一、四种扩展手段：什么时候用哪个

Unity 项目里做"可扩展"只有四条路。你的工程里四种都用了，只是没意识到自己在做选择。

| 手段 | 本质 | 适合什么 | 什么时候会变成负担 |
|---|---|---|---|
| **枚举 enum** | 一组**封闭**的种类，代码里按它分支 | 种类固定、永远只有这几项、逻辑写在代码里 | 种类会不断增加，且每加一个都要改代码 → 变成巨大 switch |
| **ScriptableObject 资产** | 一个个**数据实例**，非程序员也能建 | 数量会增长、每个实例有自己的数值、要能在 Inspector 里配 | 只有一两个实例、或者需要逻辑而不是数据 → 过度设计 |
| **接口 interface** | "**能做什么**"的能力契约 | 多个**不相关**的类都要支持同一种操作 | 只是数据结构、没有行为 → 用错了工具 |
| **继承 + 虚方法** | "**是什么**"的家族关系 | 同类事物的不同变体，**共享大量逻辑** | 变体之间差异很大、共享很少 → 继承树变成累赘 |

### 判断口诀（照这个问自己）

```
1. 「这个东西的数量会不断增加吗？加的时候我想改代码吗？」
   → 会加 且 不想改代码  →  ScriptableObject 资产

2. 「这是一组固定的种类，代码里要按它 if/switch 吗？」
   → 是  →  枚举

3. 「我问的是"它能被做什么"，还是"它是什么"？」
   → 能做什么（被打、被存、被拾取）  →  接口
   → 是什么（史莱姆/飞行怪、剑/枪）  →  继承

4. 「这几个类之间共享大量代码吗？」
   → 共享多  →  继承
   → 共享少  →  别继承，用组合（挂不同的组件）
```

## 二、用商店系统完整推演一遍

你卡住的地方就在这里。我们一个选择一个选择地过。

### 选择 1：商品用 `ShopItemData`（SO 资产）而不是枚举

**如果做成枚举**：

```csharp
// ❌ 反面写法
public enum ShopItem { HealthPotion, Key, IronSword, ... }

// 商店里每个商品的价格要写在代码里
int GetPrice(ShopItem item) {
    switch (item) {
        case ShopItem.HealthPotion: return 30;
        case ShopItem.Key:          return 30;
        ...
    }
}
```

问题：
1. **加一个商品 = 改枚举 + 改 switch + 重新编译 + 重新出包**（你现在正在做热更新，这个代价尤其大）
2. 枚举项**挂不了数据** —— 图标、回血量、描述这些没法写在枚举上，只能另找地方
3. 策划/美术想调价格，得找你改代码

**用 SO 之后**：

```
加商品 = Project 窗口右键 → Create → Data/Shop Item → 填几个字段 → 拖进 ShopData 的列表
```

**零代码、零编译、不需要你参与。** 这就是数据驱动的全部意义。

**但要能说出"什么时候枚举反而对"**：如果这个游戏只有"药水"和"钥匙"两种商品，价格还永远不变 —— 那枚举 + 常量是更简单的选择，SO 属于过度设计。

**判断的关键是"增长率"**：你以后大概率要加武器、加 buff 药水、加永久升级 → SO 的边际成本是 0，枚举的边际成本是"每次都要动代码"。

---

### 选择 2：为什么 `ShopData` 是一个 `List<ShopItemData>`，而不是接口

你的原话："我不知道是定一个可售卖接口，还是用枚举。"

**先问：商店卖的东西有"行为"吗？**

没有。一个商品就是**一堆数据**：名字、图标、价格、类型、效果参数。它不会"自己做什么"，是**玩家买了之后，商店需要做点什么**。

所以：
- **商品 = 数据** → `ShopItemData`（SO）✓
- **购买行为 = 逻辑** → 写在 `ShopPanel.TryBuy()` 里，按 `itemType` 分支 ✓

```csharp
// ShopPanel.TryBuy 的核心
if (item.itemType == ShopItemType.Weapon)
    playerCombat.AddWeapon(item.weapon);
else if (playerInventory != null)
    playerInventory.AddItem(item, 1);
```

**这里"枚举 + 分支"是对的**，因为分支只有两条，而且短期内不会爆炸。

**那什么时候才该上接口？**

当"买完要做的事"差异变大、分支变多时。比如以后有：

```
买装备     → 进装备栏
买永久升级 → 改玩家属性上限
买地图碎片 → 解锁区域
买消耗品   → 进背包
买祝福     → 加一个持续 buff
```

这时候 `TryBuy` 里就会长出一个**六七个分支的 switch**，而且每加一种都要改这个函数 —— **那一刻**才该重构成：

```csharp
public interface IPurchaseEffect { void Apply(PlayerContext ctx, ShopItemData item); }

public class AddToInventoryEffect : IPurchaseEffect { ... }
public class UnlockAreaEffect    : IPurchaseEffect { ... }
// ShopItemData 上挂一个 IPurchaseEffect 引用（或者按 itemType 查表）
```

**关键认知：接口不是"更高级的写法"，而是"分支多到 switch 撑不住时的解法"。** 提前上接口 = 为一个还不存在的问题写代码。

**面试可以这么说**：

> "商店我先用了'数据资产 + 枚举分支'的组合，因为购买效果只有两种。等效果类型增加到五六种、switch 开始难维护时，再把购买效果抽成 `IPurchaseEffect` 接口。这是演进的，不是一开始就设计出来的 —— 过早抽象会让简单的东西变复杂。"

这段话的价值远大于"我用了接口"。

### 选择 3：为什么 `PlayerWallet` 和 `PlayerInventory` 是两个组件

**职责不同**：

| 组件 | 管什么 | 变化的原因 |
|---|---|---|
| `PlayerWallet` | 一种**数值**（金币） | 加"钻石"、"灵魂"这类货币时改 |
| `PlayerInventory` | 一个**列表**（道具 + 数量） | 加"装备栏"、"材料栏"时改 |

如果合成一个 `PlayerData`：
- 掉金币要广播 `CoinChange`，捡道具要广播 `InventoryChange` —— 混在一起就没法分开通知
- 两个系统的变化节奏不一样（货币基本不变，背包会一直加东西）
- 存档时粒度和顺序也不一样

**原则：一个组件只因为一个原因而变化**（单一职责）。这不是"拆得越细越好"，而是"**变化原因不同的东西不要放在一起**"。

---

### 选择 4：为什么全都走 `EventCenter`，而不是互相引用

看这条链路：

```
CoinPickup（掉落物）→ PlayerWallet.AddCoins()
                          ↓ 广播 CoinChange
                      UIManager 更新金币文字
```

`PlayerWallet` **完全不知道 UIManager 存在**。好处：

1. **捡金币的代码不用改**，不管 UI 后面变成什么样
2. **UI 可以随时增删**（比如再加一个"金币数字飘字"，只要订阅同一个事件，`PlayerWallet` 一行不用动）
3. **不会出现循环引用**（UI 引用 Wallet，Wallet 又引用 UI → 编译期就纠缠在一起）

**代价也要知道**：事件是**运行时**连接的，编译器查不出"没人订阅"或"拼错事件名"。所以：
- 事件名统一从 `EventCenter.EventType` 枚举取（`ToString()`），而不是手写字符串 ✓ 你的项目已经这么做了
- 出了"事件发了但没反应"的问题，要主动查订阅方（你那个 `BossDefeated` 广播了但没弹面板，就是这个类型）

## 三、项目里的四种手段各用在哪（对照表）

### 枚举（封闭的种类）

| 枚举 | 取值 | 为什么是枚举而不是 SO |
|---|---|---|
| `ShopItemType` | `Weapon` / `Consumable` | 只有两类，代码里要分支，永不变 |
| `ConsumableType` | `None` / `Heal` | 同上 |
| `SfxId` | 22 项音效 | **代码要按它精确调用**（`AudioManager.Play(SfxId.Jump)`）；换成 SO 就变成按名字查，编译期查不出拼错 |
| `PoolType` | `Coin` / `HitEffect` / `Projectile` / `Ghost` | 对象池的种类，代码里要按它取池 |
| `EventCenter.EventType` | 10 个事件 | 事件名必须编译期可查，否则拼错字符串没人发现 |
| `State.StateLayer`（Lua） | `BASE` / `ACTIVE` / `ABNORMAL` | 三层固定 |

**共同特征**：**代码要按它做精确分支**。如果换成 SO，就等于"用数据决定代码走哪条路"，编译器帮不上忙。

### ScriptableObject 资产（会增长的数据）

| 资产 | 有几个实例 | 谁引用它 |
|---|---|---|
| `ShopItemData` | Key、HealthPotion… | `ShopData.items`、`Door.requiredKey` |
| `ShopData` | 1 个 | `ShopNPC.shopData` |
| `WeaponData` 子类 | IronSword、Laser、FireballData | `PlayerCombat.weaponInventory`、`ShopItemData.weapon` |
| `LootTable` | ChestLoot、SlimeLoot | `TreasureChest.lootTable`、`Enemy.lootTable` |
| `SoundLibrary` | 1 个 | `AudioManager.library` |
| `CharacterAnimConfig` | 每个怪一套 | `Enemy.animConfig` |
| `BTConfig` | 行为树 | `BTExecutor` |

**共同特征**：**数量会增长 + 需要 Inspector 配置 + 非程序员可能要改**。

### 接口（能力契约）

| 接口 | 谁实现 | 为什么是接口 |
|---|---|---|
| `IDamageable` | `PlayerHealth`、`Enemy`、`DummyEnemy`、`BTExecutor` | 武器/陷阱/弹幕只关心"**这东西能不能被打**"，不关心它是玩家还是敌人 |
| `ISaveable` | 有存档需求的组件 | 存档系统遍历所有 `ISaveable`，统一 `OnSave`/`OnLoad` |

**关键**：`IDamageable` 让 `SwordWeapon` 可以打任何东西 —— **包括你以后加的假人、可破坏的箱子**，而武器代码一行不用改。这就是接口的价值：**把"谁"和"能做什么"解耦**。

### 继承 + 虚方法（家族 + 共享逻辑）

| 基类 | 子类 | 覆写了什么 |
|---|---|---|
| `Enemy` | `SlimeEnemy` | `MoveHorizontal`（跳着走）、`UpdateVisuals`（挤压）、`CanStartAttack`（必须落地） |
| `Enemy` | `FlyingEnemy` | `GetPostHurtState`、`GetCombatReturnState`、`CanSeePlayer`（双阈值滞回） |
| `EnemyState` | 11 个状态类 | `AnimName`、`Enter`/`Exit`/`LogicUpdate`/`PhysicsUpdate` |
| `WeaponData` | `SwordWeapon` / `LaserWeapon` / `RangedWeapon` | `Attack()` 一个方法 |

**注意 `Enemy` → `SlimeEnemy` 这个例子很典型**：

```csharp
// 基类：默认"持续给速度"
public virtual void MoveHorizontal(float dir, float speed)

// 史莱姆：覆写成"间隔性地跳"
public override void MoveHorizontal(float dir, float speed)
```

**为什么这里用继承而不是组合**：因为史莱姆和飞行怪**共享 90% 的逻辑**（血量、受击、死亡、掉落、视野、状态机驱动）—— 只有"怎么移动"等少数几点不同。

**如果共享很少呢？** 比如以后加一个"炮台敌人"（不会移动、只会射击），它和史莱姆共享的可能只有血量和受击 —— 那就**不该继承 `Enemy`**，而应该把"血量+受击"抽成组件挂上去。判断标准是**共享代码的比例**。

## 四、整体分层：为什么这么排

```
┌─────────────────────────────────────────────┐
│  表现层   UI / 音效 / 特效 / 相机震动          │
│           UIManager, ShopPanel, AudioManager │
│           EnemyHealthBar, CameraShake        │
├─────────────────────────────────────────────┤
│  事件总线  EventCenter                        │
│           ↑ 只传数据，不传引用                 │
├─────────────────────────────────────────────┤
│  逻辑层   状态机 / 战斗 / 交互 / 经济          │
│           EnemyStateMachine, PlayerCombat    │
│           ShopPanel.TryBuy, Door             │
├─────────────────────────────────────────────┤
│  数据层   ScriptableObject / 枚举             │
│           ShopItemData, WeaponData, SfxId    │
└─────────────────────────────────────────────┘
```

**三条铁律**（你的项目基本都遵守了）：

1. **上层依赖下层，下层不认识上层**
   `PlayerWallet` 不知道 `UIManager` 存在；`ShopItemData` 不知道谁在卖它。

2. **同层之间用事件或接口通信，不直接引用**
   武器不引用 UI，UI 不引用武器 —— 都通过 `EventCenter`。

3. **数据在资产里，逻辑在代码里，表现可替换**
   改价格不用改代码；换 UI 不用改钱包；换音效不用改触发点。

## 五、自查清单：以后遇到"该用哪种"时照这个走

```
□ 1. 这东西的数量会增长吗？
      不会（永远这几项）→ 继续问 2
      会              → SO 资产

□ 2. 代码要按它做精确分支吗？（switch / if）
      要   → 枚举
      不要 → 常量 / 静态配置

□ 3. 我问的是"能做什么"还是"是什么"？
      能做什么 → 接口
      是什么   → 继承（先看共享代码多不多，少的话用组合）

□ 4. 两个系统之间需要通信吗？
      需要 → 优先问"能不能用 EventCenter 广播"
             只有在"必须同步拿到返回值"时才直接引用

□ 5. 这个数值以后可能要调吗？
      要 → 放 Inspector / SO
      不要 → 常量（但留个注释说明为什么写死）
```

## 六、这套思路怎么讲给面试官听

不要讲"我用了观察者模式、工厂模式、策略模式" —— 这句话没有信息量。

**讲你的判断过程**：

> "做商店的时候我先想的是用枚举还是用 ScriptableObject。
> 枚举的问题是每加一个商品都要改代码、重新编译，而我这个项目是走 Lua 热更新的，编译成本很高；
> 而且商品各自有价格、图标这些数据，枚举项上挂不了。
> 所以商品做成 SO 资产 —— 加商品是'右键新建一个资产 + 填字段'，零代码改动。
>
> 但**商品类型**我用了枚举（武器/消耗品），因为类型只有两种、代码里要按它分支，
> 这种'封闭且需要精确分支'的东西用枚举比用资产更安全 —— 编译器能帮你查拼写。
>
> 购买效果我暂时写在一个 `TryBuy` 里按类型分支。**以后效果类型多了、switch 撑不住了，
> 才会抽成 `IPurchaseEffect` 接口**。这是规模驱动出来的重构，不是一开始就设计的。"

**这段话展示的是**：你知道每种手段的适用边界、知道成本在哪、知道什么时候该演进。**这比"我会设计模式"强十倍**，因为它证明你在做工程判断而不是套模板。
