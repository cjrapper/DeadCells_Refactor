## 二、一次购买，数据怎么流

```
按 F（将来是 NPC 交互）
   ↓
ShopPanel.Open(shopData)
   ├─ FindObjectOfType 拿到 playerInput / wallet / inventory
   ├─ playerInput.InPutLocked = true      ← 玩家动不了
   ├─ currentShop = shopData              ← 存起来，Refresh 要用
   ├─ content.SetActive(true)             ← 显示
   └─ Refresh()
        ├─ 清空 content 的所有子物体
        ├─ 建标题
        └─ foreach 商品 → CreateRow(item, y); y += 55
             ├─ 行容器（锚顶部、横向拉伸、高 55）
             ├─ 左文字 = item.itemName
             ├─ 右文字 = $"{item.price} G"
             └─ 按钮 → onClick = () => TryBuyItem(item)   ← 闭包捕获 item

点击 Buy
   ↓
TryBuyItem(item)
   ├─ wallet.TrySpendCoins(item.price)
   │    ├─ false → Debug.Log("钱不够") + 按钮变淡
   │    └─ true  → inventory.AddItem(item, 1)   ← 发货
   │              └─ Refresh()                   ← 重建列表，颜色/状态刷新
   └─
   注意：钱包内部会广播 CoinChange，HUD 那边自己更新，商店不用管

按 G
   ↓
ShopPanel.Close()
   ├─ content.SetActive(false)
   └─ playerInput.InPutLocked = false     ← 恢复操作
```

## 三、`Awake` 和 `CreateRow` 到底差在哪

你的疑问："两处都在创建 UI，大致相同却又不同。"

**它们干的不是同一类事：**

| | `Awake` | `Refresh` / `CreateRow` |
|---|---|---|
| 建什么 | **结构**：容器、背景 | **内容**：商品列表 |
| 建几次 | **1 次**（物体一生只一次） | **每次刷新都重建** |
| 数据来源 | 写死的配置（颜色、尺寸） | **`ShopData` 里的数据** |
| 生命周期 | 和物体一样长 | 刷新一次就销毁 |
| 变了会怎样 | 改布局结构 | 改商品内容 |

> **一句话**：**`Awake` 建"面板长什么样"，`CreateRow` 建"面板里装什么"。**
> 前者是**骨架**，后者是**填充**。

**所以"大致相同"是因为两者都在 `new GameObject`；"不同"是因为一个只做一次，一个反复做。**

## 四、你"感觉差点什么"—— 差的是这个

`ShopPanel` 这一个类，现在同时干了**三件性质不同的事**：

| # | 职责 | 代码位置 | 变化的原因 |
|---|---|---|---|
| ① | **对象生命周期** | `Awake` / `Instance` / `Open` / `Close` | 改初始化顺序、改单例策略 |
| ② | **UI 构建** | `Refresh` / `CreateRow` | 改布局、加元素、调间距 |
| ③ | **业务逻辑** | `TryBuyItem` | 加限购、加武器、打折、加确认弹窗 |

**这三件事"变化的理由"完全不同。**

- 你要改布局 → 只该动 ②
- 你要加限购规则 → 只该动 ③
- 你要改"商店默认关闭" → 只该动 ①

**现在它们缠在一个文件里，所以你说不出"ShopPanel 到底是干嘛的"** —— 因为它干的不是一件事。

### 这就是 SOLID 里的 "S"（单一职责）

**注意：单一职责不是"一个类只能有一个方法"**，是：

> **一个类应该只有一个"引起它变化的原因"。**

`ShopPanel` 现在有**三个**变化原因。这就是你"吃不透"的真实来源 —— **不是你理解不了，是这个类本身还没有清晰的形状。**

### 这不代表你写错了

对学习项目来说，**一个文件写完是最好的**：你亲眼看到三件事怎么长到一起，才知道为什么要拆。

**先让它工作，再考虑拆** —— 顺序反了就是空谈架构。

## 五、如果以后要拆，怎么拆

**不是现在做，是让你知道路在哪儿：**

| 拆出来的东西 | 负责什么 | 大概长什么样 |
|---|---|---|
| `ShopPanel`（View） | 只建 UI、只显示 | 提供 `Show(shop)` / `Hide()` / `RefreshGold()` |
| `ShopController`（逻辑） | 校验、扣钱、发货 | `TryBuy(item)` 返回结果 |
| 数据 | `ShopData` / `ShopItemData` | 已有 |

**好处**：改布局不碰规则，改规则不碰布局。

**代价**：多两个类、多一层调用。

**判断标准**：**当"改 A 经常不小心改坏 B"的时候，就该拆了。** 现在还没到。

# 八、数据层的关系（最重要的一张图）

## 8.1 三个东西，一条线

```
┌─────────────────────────────────────────────────────────┐
│  数据层（资产 .asset，不是代码）                          │
│                                                           │
│  ShopData.asset ──── items ────┐                         │
│     shopName = "SHOP"           │                         │
│                                 ▼                         │
│              HealthPotion.asset     Key.asset            │
│              (ShopItemData)         (ShopItemData)       │
│                    │                                      │
│                    └── weapon ──→ Sword.asset             │
│                                   (WeaponData)            │
└─────────────────────────────────────────────────────────┘
                          │ 运行时读取
                          ▼
┌─────────────────────────────────────────────────────────┐
│  表现 + 逻辑层（代码）                                    │
│                                                           │
│  ShopPanel                                                │
│    ├─ currentShop : ShopData    ← 指向上面那家店          │
│    ├─ Refresh()  → 遍历 items → CreateRow                │
│    └─ TryBuyItem(item)                                    │
│          ├─ wallet.TrySpendCoins(item.price)              │
│          └─ 按 itemType 决定【交付方式】                   │
└─────────────────────────────────────────────────────────┘
```

| 谁 | 负责 | 它变化时你改什么 |
|---|---|---|
| `ShopItemData` | **一件商品是什么** | 改单品配置（名字/价格/图标/效果） |
| `ShopData` | **这家店卖哪些** | 加减商品 |
| `ShopPanel` | **怎么展示 + 怎么成交** | 改 UI 布局，或改买卖规则 |

## 8.2 ⚠️ 数据不是代码存进去的，是在 Inspector 里拖的

```csharp
public List<ShopItemData> items = new();   // ← 代码里从来没有 items.Add()
```

**列表内容在 `.asset` 文件里**，是你在编辑器里配的：

```
选中 ShopData.asset → Inspector 里 Items 列表 Size = 2
  → Element 0 拖入 HealthPotion.asset
  → Element 1 拖入 Key.asset
```

`foreach (var item in currentShop.items)` 遍历的就是**你手工配好的那些商品**。

> **这就是"数据类代码很少，却感觉差什么"的原因** ——
> **数据的内容不在代码里，在资产里。** 看代码只能看到字段声明，看不到"卖的是什么"。

## 8.3 `itemType` 不是"物品分类"，是"**交付方式**"

```csharp
if (item.itemType == ShopItemType.Weapon)
    playerCombat.AddWeapon(item.weapon);      // 交付方式 A
else
    playerInventory.AddItem(item, 1);         // 交付方式 B
```

**它决定的不是"这是什么物品"，是"买完怎么给你"。**

| 交付方式 | 例子 | 调谁 |
|---|---|---|
| 进背包 | 药水、钥匙 | `PlayerInventory.AddItem` |
| 进武器栏 | 武器 | `PlayerCombat.AddWeapon` |
| 直接加货币 | 金币包、特殊货币 | `PlayerWallet.AddCoins` |
| 直接加状态 | Buff、临时护盾 | 对应状态系统 |
| 解锁功能 | 技能、传送点 | 对应系统 |

> **"有些东西不能进背包"不是例外，是第 3、4、5 种交付方式。**
> **判断标准**：买完之后是"**塞进某个容器**"还是"**立刻改变状态**"？

## 8.4 数据为什么放在那个类里 —— "信息专家"原则

| 数据 | 放在哪 | 为什么 |
|---|---|---|
| `Coins` | `PlayerWallet` | 钱的变化要校验 + 广播 |
| 消耗品 `slots` | `PlayerInventory` | 只有背包在增删 |
| 武器 `weaponInventory` | `PlayerCombat` | **攻击每帧都要读当前武器** |
| 商品配置 | `ShopData`（SO） | 编辑器里配，运行时只读 |

> **数据放在"最常用它的类"里，操作数据的方法跟着数据走。**（信息专家模式）
>
> 武器在 `PlayerCombat` 而不是 `PlayerInventory`，因为攻击是最热的路径 ——
> 不能每次攻击都先去背包问"我拿的什么武器"。
>
> **后果**：商店不需要知道武器存在哪个字段，只需要知道"**谁能加武器**"。
> 你换掉 `PlayerCombat` 内部的存储方式，商店那行代码不用改 —— 这就是解耦。

## 8.5 武器支持要做什么（两步，不只是建 SO）

**① 数据**
1. 建 `WeaponData` 资产（武器本体：伤害、冷却、外观）
2. 建 `ShopItemData` 资产，`itemType = Weapon`，`weapon` 指向那个 `WeaponData`
3. 把它拖进 `ShopData.items`

**② 代码**
- `ShopPanel` 加一个 `PlayerCombat` 字段，`Open()` 里取
- `TryBuyItem` 里加武器分支，调 `playerCombat.AddWeapon(item.weapon)`

**光建数据不够** —— 没分支的话，买武器会走"进背包"那条路，
而背包存的是 `ShopItemData`，武器需要 `WeaponData`，类型对不上。
