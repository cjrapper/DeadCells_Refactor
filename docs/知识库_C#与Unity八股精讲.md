# 一、C# 语言基础

## 1.1 接口与抽象类 ★★★

### 一句话结论
**接口描述"能做什么"（能力契约），抽象类描述"是什么"（继承血缘）。C# 是单继承、多实现。**

### 先看例子（用你自己项目里的东西）

```csharp
// ========== 接口：一份能力契约 ==========
// 任何东西，只要能受伤，都可以实现它 —— 不关心它到底是什么
public interface IDamageable
{
    void TakeDamage(int damage, Vector2 knockback);
    bool IsDead { get; }
}

// ========== 抽象类：一个家族的共同底座 ==========
public abstract class Enemy : MonoBehaviour, IDamageable
{
    public int maxHealth = 100;           // ★ 可以有字段 —— 接口做不到
    protected int currentHealth;

    public virtual void MoveHorizontal(float dir) { /* 默认实现 */ }  // ★ 可以有身体
    public abstract void DoAttack();                                  // 只有签名，子类必须实现

    public virtual void TakeDamage(int damage, Vector2 knockback) { /* ... */ }
}

// 史莱姆"是一种"敌人 —— 继承
public class SlimeEnemy : Enemy
{
    public override void DoAttack() { /* 必须实现 */ }
    public override void MoveHorizontal(float dir) { /* 覆写成"跳着走" */ }
}

// 玩家"不是"敌人，但也能受伤 —— 实现接口
public class PlayerHealth : MonoBehaviour, IDamageable { /* ... */ }
```

### 三层区别，一层层说清楚

**第一层：能放什么成员**

**接口** —— 只能放**方法、属性、事件、索引器的签名**。
- 只有名字，没有身体（C# 8 之前完全不能有实现）
- ❌ 不能有**实例字段**（`int maxHealth;` 不合法）
- ❌ 不能有**构造函数**
- 成员默认 `public`，不能加访问修饰符

> **为什么？** 因为接口是**契约**。契约只规定"你能做什么"，不规定"你内部怎么存数据"。**怎么存是实现者自己的事**，接口不该管。

**抽象类** —— 它就是一个**普通的类**，唯一的特殊之处是不能被实例化。
- 字段、构造函数、各种访问修饰符：全都可以有
- `abstract` 方法：只有签名，子类**必须** `override`
- `virtual` 方法：有实现，子类**可以**覆写，也可以不管
- 普通方法：子类直接继承

**第二层：能继承几个**

- **接口**：一个类可以实现**多个** → `class Door : MonoBehaviour, IInteractable, ISaveable` ✓
- **抽象类**：一个类只能继承**一个** → `class Door : Enemy, MonoBehaviour` ❌

这就是 **C# 单继承多实现** 的含义。（C++ 可以多继承，C# 故意去掉了，避免菱形继承那类问题。）

**第三层：实际该用哪个**

判断只有一条：**这两个类之间是什么关系？**

| 关系 | 用什么 | 例子 |
|---|---|---|
| "**是一种**"（is-a） | **抽象类** | 史莱姆是一种敌人，飞龙也是一种敌人，共享血量/受击/寻路代码 → `Enemy` |
| "**能做什么**"（can-do） | **接口** | 玩家不是敌人，宝箱也不是敌人，但它们都能"被伤害"或"被交互" → `IDamageable` |

### 两个容易混的点

**① 接口不能实例化，是因为"它只定义功能"吗？**

**不是。抽象类也不能实例化。** 两者不能 `new` 的原因是同一个：

> **它们都是"不完整的类型"—— 有成员只有声明没有实现。既然实现不完整，`new` 出来也没法用。**

```csharp
IDamageable d = new IDamageable();   // ❌ 编译错误
Enemy e = new Enemy();               // ❌ 也编译错误（abstract）
```

所以"不能实例化"**不是接口独有的特性**，跟"定义功能"也没有因果关系。**把这两件事绑在一起答，面试官会认为你没理解。**

**② 那多态体现在哪？**

多态**不**体现在"不能实例化"，而体现在这里：

```csharp
// 变量的声明类型是接口，运行时才知道真正是谁
IDamageable target = hit.GetComponentInParent<IDamageable>();
target.TakeDamage(10, knockback);
```

同一行 `target.TakeDamage(...)`：
- 如果 `target` 实际是 `PlayerHealth` → 走玩家的扣血 + 无敌帧 + 闪烁
- 如果 `target` 实际是 `Enemy` → 走敌人的扣血 + 击退 + 脱战回血

**调用方完全不关心是谁。** 这就是运行时的动态绑定 —— **用抽象类型的引用，调用具体类型的实现**。你的 `EnemyHitUtil` 做的就是这件事。

### 方法体是什么（搞清这个，abstract 和 virtual 就通了）

**方法体 = 大括号里的那段代码。**

```csharp
public int Add(int a, int b)     // ← 方法签名：叫什么、要什么参数、返回什么
{
    return a + b;                // ← 方法体：具体怎么算
}
```

| 修饰符 | 有方法体吗 | 基类能自己实现吗 | 子类必须实现吗 |
|---|---|---|---|
| 普通方法 | ✅ 有 | ✅ 能 | ❌ 不能覆写 |
| `virtual` | ✅ 有 | ✅ 能，有默认行为 | ❌ 可选，覆写不覆写都行 |
| `abstract` | ❌ **没有** | ❌ **不能** | ✅ **必须** |

> **一句话**：方法体代表"**基类已经知道怎么做了**"。
> 有方法体 → 基类能兜底，子类随意；没有方法体 → 基类也不知道怎么做，只能甩给子类。

**所以 `abstract` 和 `virtual` 不是"程度不同"，是"有没有实现"的区别。**

再补两条：
- **`abstract` 成员只能写在 `abstract class` 里**，普通类不能有 abstract 成员
- **`abstract` 不能用在字段上**（`public abstract int hp;` ❌ 编译错误），只能用于方法、属性、事件、索引器

### ✅ 标准复述（照着背这段）

> "抽象类就是一个普通类，只是不能实例化。它可以有字段、构造函数、普通方法、虚方法，也可以有抽象方法。
>
> **抽象方法和虚方法的区别是：虚方法有实现，子类可以不覆写；抽象方法只有声明、没有实现，子类必须实现** —— 除非子类自己也是抽象类。而且抽象成员只能写在抽象类里。
>
> 接口是一份能力契约，只能有方法、属性、事件、索引器的签名，**不能有实例字段和构造函数**。一个类可以实现多个接口，但只能继承一个抽象类，C# 是单继承多实现。
>
> **两者都不能实例化，因为它们都有未实现的成员，属于类型不完整。**"

### 补充版（如果面试官要你展开三层区别）

> "接口和抽象类都是 C# 实现运行时多态的手段，区别分三层。
>
> **第一，成员限制。** 接口只能放方法、属性、事件、索引器的签名，不能有实例字段和构造函数；抽象类就是一个普通类，只是不能实例化，字段、构造函数、访问修饰符都可以有。
>
> **第二，继承数量。** 一个类可以实现多个接口，但只能继承一个抽象类 —— C# 是单继承、多实现。
>
> **第三，怎么选。** 接口描述'能做什么'，是能力契约，用在互不相关的类之间；抽象类描述'是什么'，用在共享大量代码的同一个家族里。"

### 追问预判

**Q：抽象类的抽象方法，在派生类中不实现，允许吗？**
A：**派生类如果也是 `abstract`，允许；如果不是 `abstract`，必须 `override`，否则编译报错。**

**Q：接口可以有实现吗？**
A：C# 8 起可以有默认实现（default interface method），但传统笔试题按"接口不能有实现"答，如果面试官追问再补这句。

## 1.2 装箱与拆箱 ★★

### 一句话结论
**装箱是值类型转成 `object`/接口，在堆上分配内存并复制；拆箱是反向，先类型检查再复制回栈。危害是装箱产生堆分配，频繁装箱会加重 GC。**

### 展开

**装箱（Boxing）**：值类型 → `object` 或接口类型
1. 在**托管堆**上分配内存
2. 把值类型的数据**复制**进去
3. 返回该对象的引用

**拆箱（Unboxing）**：`object` → 值类型
1. **类型检查**：检查对象是不是目标值类型，不是就抛 `InvalidCastException`
2. 把堆上的值**复制**回栈

**开销分别在哪**：
- 装箱 → **堆分配**（这才是 GC 压力的来源）
- 拆箱 → **类型检查 + 内存复制**（注意：不是"CPU 算力消耗"，说这个不专业）

### 两个必答的延伸

**① 泛型集合不会装箱**
- `List<int>` → **不装箱**
- `ArrayList`（内部存 `object`）→ **每次增删改都装箱**

这是最常考的延伸，答出来就比只会背定义的人高一档。

**② 装箱是复制，不是引用**
装箱之后修改原来的值类型变量，**不会影响已装箱的对象**。反过来也一样。

### ✅ 答题模板

> "装箱是把值类型转成 object 或接口类型：在托管堆上分配内存、把值复制进去、返回引用。拆箱是反向：先做类型检查，类型不符抛 InvalidCastException，再把值复制回栈。
>
> 危害主要在装箱，因为它产生堆分配，频繁装箱会加剧 GC 压力。所以能用泛型集合就不用非泛型 —— List&lt;int&gt; 不装箱，ArrayList 会装箱。"

### 项目对应
你用 `Physics2D.OverlapCircleNonAlloc` 代替 `OverlapCircle`，就是为了避免每次调用都 `new` 一个 `Collider2D[]`。**这是"避免托管堆分配"的直接实践，面试官问 GC 时这就是实锤。**

## 1.3 GC：.NET 与 Unity 的区别 ★★★

### 一句话结论
**这是两个不同的 GC。.NET 是分代 + 标记清除压缩；Unity 用的是 Boehm，非分代、非压缩，靠增量式 GC 摊平峰值。面试官问哪个就答哪个，别混。**

### 【A】.NET 的 GC

**分代式（Generational）**
- `Gen0`：新对象，回收最频繁、最快（存活对象少）
- `Gen1`：Gen0 存活下来的，作为缓冲
- `Gen2`：长期存活对象，回收最慢（Full GC）
- `LOH`（Large Object Heap）：≥ 85000 字节的大对象直接进这里

**三个阶段：标记 → 清除 → 压缩**
1. **标记（Mark）**：从根（栈变量、静态字段、寄存器）出发，遍历所有可达对象
2. **清除（Sweep）**：回收不可达的对象
3. **压缩（Compact）**：移动存活对象、更新引用、**消除内存碎片**

**触发时机**：Gen0 满 / 分配时空间不足 / 手动 `GC.Collect()`

**STW（Stop-The-World）**：GC 期间暂停托管线程 → 游戏掉帧

### 【B】Unity 的 GC —— 和 .NET 不是一回事

**Unity 用的是 Boehm–Demers–Weiser GC，非分代、非压缩。**

| | .NET GC | Unity 的 Boehm GC |
|---|---|---|
| 分代 | 有（Gen0/1/2 + LOH） | **无** |
| 压缩 | 会压缩，能消除碎片 | **不压缩**，碎片消不掉 |
| 对策 | 分代本身就是优化 | **增量式 GC** |

**增量式 GC（Incremental GC）**：
- **默认开启**（Project Settings > Player > Configuration > Use Incremental GC）
- 把一次完整 GC **拆到多帧**执行，而不是一次性 stop-the-world
- **不会让 GC 总体变快**，但把峰值摊平了，帧率更稳
- 代价：引入 **write barriers**，引用变化时要通知 GC，托管代码有额外开销
- 标记阶段被打断后，如果引用频繁变化，可能反复重扫，极端情况退化成完整 GC
- **WebGL 不支持增量式 GC**

**怎么观察**：Profiler → CPU Usage 模块的 **GC Alloc** 列，看每帧分配了多少字节。

### ✅ 答题模板

> "要分开说。**.NET 的 GC 是分代式的**：Gen0/Gen1/Gen2 加 LOH 大对象堆，流程是标记、清除、压缩三步，从根对象出发标记可达对象，回收不可达的，再压缩消除碎片。GC 期间会 Stop-The-World，暂停托管线程。
>
> **Unity 的 GC 和这个不一样。** Unity 用的是 Boehm，**非分代、非压缩**，所以内存碎片消除不了。Unity 的对策是**增量式 GC**，默认开启，把一次 GC 摊到多帧执行，不一次性停主线程。它不会让 GC 变快，但能消除 GC spike。代价是多了 write barrier 的开销。"

### 追问预判

**Q：怎么减少 GC？**
1. **对象池** —— 弹幕、特效、金币这类高频对象复用
2. **不在 Update 里 new** —— 包括字符串拼接、`new WaitForSeconds`
3. **用 NonAlloc API** —— `OverlapCircleNonAlloc` / `RaycastNonAlloc`
4. **避免装箱** —— 用泛型集合，别用 `object` 参数
5. **字符串用 `StringBuilder`**
6. ⚠️ **注意**：`GetComponent` 在**编辑器里每次都会分配内存**，打包后不会。所以性能数据要在真机 Development Build 上测。

## 1.4 Mono 与 IL2CPP ★★

### 一句话结论
**两者都是 C# → IL，区别在 IL 之后：Mono 运行时 JIT 编译成机器码，IL2CPP 先把 IL 转成 C++ 再编译成原生码。**

| | Mono | IL2CPP |
|---|---|---|
| 执行方式 | 运行时 **JIT** | IL → **C++ 代码** → 原生编译器编译 |
| 运行性能 | 较低 | **较高** |
| 构建速度 | 快 | **慢** |
| 反编译难度 | 容易 | **难**（已是原生码） |
| iOS | **不支持**（iOS 禁 JIT） | **必须用** |
| 包体 | 较小 | 通常更大 |

### ✅ 答题模板
> "两者都是先把 C# 编成 IL。Mono 是运行时用 JIT 把 IL 编成机器码，构建快但性能一般，而且 iOS 不允许 JIT 所以用不了。IL2CPP 是把 IL 先转成 C++ 代码，再用平台原生编译器编成机器码，运行性能更好、更难反编译，代价是构建慢、包体大。iOS 必须用 IL2CPP。"

# 二、数据结构

## 2.1 哈希表的底层原理 ★★★

### 一句话结论
**哈希表 = 数组 + 哈希函数。查找时先算哈希定位到桶，然后在桶里先比哈希值、再比 key，两步都要。**

### 存储过程
1. 对 key 计算 **哈希值 h**
2. `h % 桶数量`（或位运算）得到 **桶下标**
3. 把键值对存进该桶

### 哈希冲突
**不同的 key 算出了相同的桶下标。**

**两种解决办法**：
1. **链地址法 / 拉链法（Separate Chaining）**：每个桶挂一个链表，冲突的元素追加到链表上。
   → **C# 的 `Dictionary`、Java 的 `HashMap` 都用这个。**
2. **开放寻址法（Open Addressing）**：不挂链表，按规则找下一个空位 —— 线性探测、二次探测、双重哈希。

### 查找过程（面经明确问的就是这一步）

1. 算 key 的哈希值 → 定位到桶
2. 遍历桶里每个元素：
   - **先比较哈希值是否相等**
   - 哈希值相等后，**再用 `Equals` 比较 key 是否相等**
3. 两者都相等才算命中

> **为什么必须比两次？**
> 因为**哈希值相同不代表 key 相同**（这正是冲突的定义）。哈希相等只是**必要条件，不是充分条件**。
> 所以"索引上的哈希值是否相等"这个问题 —— **是的，先比哈希再比 key，两步都不能省。**

### 另外两个要点
- **装载因子**：元素数 / 桶数。超过阈值就**扩容 + 重新哈希（Rehash）**所有元素
- **时间复杂度**：平均 **O(1)**，最坏 **O(n)**（全部冲突退化成链表）

### ✅ 答题模板
> "哈希表底层是数组加哈希函数。存的时候对 key 算哈希值，取模定位到桶下标。
>
> 不同 key 算出同一个下标就是**哈希冲突**。解决办法主流是**链地址法**，每个桶挂一个链表；另一种是**开放寻址法**，冲突了就按规则找下一个空位。C# 的 Dictionary 用的是链地址法。
>
> 查找的时候，先算哈希定位到桶，然后在桶里**先比哈希值，再比 key**。两步都要，因为哈希相等不代表 key 相等，那只是冲突。"

## 2.2 二叉树遍历与非递归结束条件 ★★

### 一句话结论
**递归的终止条件是"节点为 null"；非递归的结束条件是"栈（或队列）为空"。这两个问的不是一回事。**

### 四种遍历

| 遍历 | 顺序 | 用什么 | 循环条件 |
|---|---|---|---|
| 前序 | 根 → 左 → 右 | 栈 | `while (栈非空)` |
| 中序 | 左 → 根 → 右 | 栈 + 当前指针 `cur` | `while (栈非空 \|\| cur != null)` |
| 后序 | 左 → 右 → 根 | 双栈法 / 记录 `lastVisited` | `while (栈非空)` |
| 层序 | 逐层从左到右 | **队列** | `while (队列非空)` |

**中序为什么要 `|| cur != null`**：一开始栈是空的，但还要一路向左压栈，所以循环条件必须同时看栈和当前指针。**这是最容易被追问的一处。**

**层序为什么用队列**：队列先进先出，保证按层从左到右；用栈会变成深度优先。

### ✅ 答题模板
> "递归的终止条件是节点为空就返回。非递归用显式栈，结束条件是栈空。前序是根入栈、弹出访问、右左入栈；中序要配一个当前指针，条件是栈非空或者指针非空，因为一开始栈是空的但还要一路往左压；后序可以用双栈或者记录上一次访问的节点。层序遍历用队列，结束条件是队列空。"

## 2.3 树的性质：满二叉树 / 完全二叉树

### 满二叉树（Perfect Binary Tree）
- 深度为 `k` → 节点总数 = **2^k − 1**
- 第 `i` 层有 **2^(i−1)** 个节点
- 叶子节点数 = **2^(k−1)**

> ⚠️ **必知的术语坑**：中文教材的"满二叉树"对应英文 **perfect binary tree**；而英文的 **full binary tree** 指的是"每个节点有 0 个或 2 个子节点"。**中文面试按中文定义答，别被英文术语绕进去。**

### 完全二叉树（Complete Binary Tree）
- 除最后一层外都满，最后一层节点**靠左连续**
- `n` 个节点 → 深度 = **⌊log₂n⌋ + 1**
- **可以用数组存储**，不浪费空间
- 数组下标关系（0-based）：父 = `(i-1)/2`，左子 = `2i+1`，右子 = `2i+2`
- **堆（优先队列）就是完全二叉树**

### 其它常考的树
| 类型 | 性质 |
|---|---|
| **二叉搜索树 BST** | 左 < 根 < 右，**中序遍历结果有序** |
| **平衡二叉树 AVL** | 任意节点左右子树高度差 ≤ 1 |
| **红黑树** | 弱平衡，增删查都是 O(log n)，C# 的 `SortedDictionary` 内部就是它 |

## 2.4 图：有向无向、邻接矩阵与邻接表

### 有向图 vs 无向图

| | 有向图 | 无向图 |
|---|---|---|
| 边 | 有方向，A→B **不代表** B→A | 无方向，A—B 即 B—A |
| 术语 | 边叫**弧**，分**入度 / 出度** | 只有**度** |
| 边数上限 | `n(n−1)` | `n(n−1)/2` |

### 两种存储方式

**邻接矩阵**：二维数组 `matrix[i][j]`
- ✅ **O(1) 判断两点是否相邻**
- ❌ 空间 **O(n²)**，稀疏图严重浪费
- 特点：**无向图的邻接矩阵一定对称**

**邻接表**：每个顶点挂一个链表/数组，记录它的邻居
- ✅ 空间 **O(n + e)**，稀疏图很省；遍历某点的邻居很快
- ❌ 判断两点是否相邻要 O(度数)

### ✅ 选择标准
> **稠密图用邻接矩阵，稀疏图用邻接表。**
> 游戏里的寻路（A*）基本都用邻接表，或者直接用网格。

## 2.5 数组实现栈

### 一句话结论
**关键就一个：`top` 指针初始为 −1，表示空栈。Push 是 `data[++top]`，Pop 是 `data[top--]`。**

```csharp
class ArrayStack<T>
{
    private T[] data;
    private int top = -1;              // ★ 初始 -1 = 空栈

    public ArrayStack(int capacity) { data = new T[capacity]; }

    public void Push(T value)
    {
        if (top == data.Length - 1) throw new InvalidOperationException("栈满");
        data[++top] = value;           // ★ 先 ++，再赋值
    }

    public T Pop()
    {
        if (top == -1) throw new InvalidOperationException("栈空");
        return data[top--];            // ★ 先取值，再 --
    }

    public T Peek()
    {
        if (top == -1) throw new InvalidOperationException("栈空");
        return data[top];
    }

    public bool IsEmpty => top == -1;
    public int Count => top + 1;
}
```

### 要说出来的三个点
1. `top` 初始 **−1**，所以"栈空"是 `top == -1`，**不是 `top == 0`**
2. `Push` 是 `data[++top]`，`Pop` 是 `data[top--]`，**自增自减的顺序不能反**
3. 这是**定长数组**，满了要抛异常或扩容（扩容一般翻倍，均摊 O(1)）

# 三、设计模式

## 3.1 SOLID 五大原则 ★★

### 一句话结论
**记忆口诀：单 开 里 接 依。**

| 字母 | 原则 | 一句话定义 |
|---|---|---|
| **S** | 单一职责 SRP | 一个类**只有一个引起它变化的原因**，只负责一件事 |
| **O** | 开闭原则 OCP | **对扩展开放，对修改关闭** —— 加功能靠加新代码，不改老代码 |
| **L** | 里氏替换 LSP | **子类必须能替换父类**而不破坏程序正确性 |
| **I** | 接口隔离 ISP | 不强迫类实现它**用不到**的方法；多个专用接口优于一个臃肿大接口 |
| **D** | 依赖倒置 DIP | **高层模块不依赖低层模块，都依赖抽象** |

### 开闭原则的标准表述
> "软件实体（类、模块、函数）应该**对扩展开放、对修改关闭**。实现手段是**抽象 + 多态**：把变化点抽成接口或虚方法，新增行为时写新实现，不动调用方。"

### 项目对应（你的四种扩展机制正好是 OCP 的四种落地）
| 机制 | 什么时候用 |
|---|---|
| **枚举** | 种类固定、需要代码分支（`SfxId`、`ShopItemType`） |
| **ScriptableObject** | 数据会持续增长、要策划配（`WeaponData`、`ShopData`、`LootTable`） |
| **接口** | 能力契约，不相关的类都要实现（`IDamageable`、`ISaveable`） |
| **继承 + 虚方法** | 同一家族共享大量逻辑（`Enemy` → `SlimeEnemy` / `FlyingEnemy`） |

---

## 3.2 里氏替换原则的实际应用 ★★

### 一句话结论
**子类可以替换父类，且不破坏程序的正确性。落地成两条硬规则：前置条件不能加强，后置条件不能削弱。**

### 两条硬规则
- **前置条件不能加强**：子类不能比父类要求更多（不能缩小参数范围、不能要求父类没要求的状态）
- **后置条件不能削弱**：子类不能比父类承诺更少（不能少做事、不能返回父类不会返回的结果）

### 经典反例：正方形继承长方形
长方形有"设宽不影响高"的约定；正方形设宽会连带改高，**破坏了这个约定**。于是任何"把正方形当长方形用"的代码都会出错 —— 继承在语法上成立，在**语义**上不成立。

**另一个常见违反**：子类抛出父类没有声明的异常。

**正确做法**：用**组合**或**接口**代替不合适的继承。

> ⚠️ **易错**：里氏替换**不是**在问工厂模式。工厂方法属于**开闭原则 / 依赖倒置**的范畴。

### 项目对应（这题你有真实案例，一定要用）
- **正例**：`Enemy.MoveHorizontal` 是虚方法，`SlimeEnemy` 覆写成"跳着走"。但它仍然满足基类约定 —— **"沿水平方向移动"**，只是实现方式不同。**这就是合法的里氏替换。**
- **另一个正例**：`IDamageable` 让玩家和敌人共用同一套伤害逻辑。
- **可以主动说的坑**：我曾把同一个伤害判定复制到多个状态类里，导致修了一处漏了另一处。**从设计原则看，这违反了 DRY，正确做法是抽成公共方法。**

# 四、Unity UGUI（面经密度最高，优先背）

> 面经里 UGUI 占了**六道题**，而且全是基础题。**客户端岗必考区，投入产出比最高，先背这块。**

## 4.1 Canvas 三种渲染模式 ★★★

### 一句话结论
**Overlay 直接渲染到屏幕、不经过相机，所以不需要相机 —— 跟 Sort Layer 无关。**

| 模式 | 渲染方式 | 需要相机吗 | 特点 |
|---|---|---|---|
| **Screen Space - Overlay** | 直接渲染到屏幕，**在所有内容最上层** | **不需要** | 永远不被遮挡；不受相机影响；随分辨率自动缩放 |
| **Screen Space - Camera** | 渲染到指定相机前方的一个平面上 | **需要** | 会被该相机前方的物体遮挡；可设 `Plane Distance` |
| **World Space** | Canvas 是场景里的普通 3D 物体 | **需要** | 可被遮挡、可缩放旋转；用于血条、名牌、VR UI |

### ⚠️ 高频错误
**"Overlay 排在最前面所以不需要相机"—— 错。**
Overlay 不是因为排序靠前，而是因为**它根本不走相机这条路**。这是因果搞反了。

### 规范回答：Overlay 为什么不需要相机？
> **因为 Overlay 模式的 Canvas 由 UI 系统直接渲染到屏幕缓冲区，不参与任何相机的视锥剔除和投影矩阵计算。**
>
> 换句话说，它不是"被相机看见"，而是"被直接贴到屏幕上"。所以场景里一个相机都没有，Overlay Canvas 照样显示。
>
> 另外两种模式必须指定相机，因为需要相机把 Canvas 从世界空间投影到屏幕空间。

**加分补充**：VR 里不能用 Overlay，因为 VR 需要双眼渲染和正确空间深度，Overlay 是平面贴图，会破坏立体感。

## 4.2 RectTransform 与 Transform 的区别 ★★★

### 一句话结论
**`RectTransform` 继承自 `Transform`，多出来的那个"位置"是 `anchoredPosition` —— 相对锚点的位置。**

| 成员 | 含义 |
|---|---|
| **`anchoredPosition`** | ★ **相对于锚点的位置**（像素）—— 就是"多出来的那个位置" |
| `anchorMin` / `anchorMax` | 锚点，归一化 0~1，相对父 RectTransform |
| `pivot` | 自身轴心，归一化坐标 |
| `sizeDelta` | 尺寸。锚点重合时 = 实际大小；锚点分开时 = 相对父级的差值 |
| `offsetMin` / `offsetMax` | 相对锚点的四边偏移 |

### 三个"位置"必须分清
- `position` → **世界坐标**
- `localPosition` → 相对**父物体**
- `anchoredPosition` → 相对**锚点** ← **UI 布局用这个**

### UI 自适应的原理
靠 `anchorMin` / `anchorMax`：**锚点重合 → 固定大小；锚点分开 → 随父级拉伸。**

## 4.3 Layout Group 三兄弟 ★★

| 组件 | 排列方式 |
|---|---|
| **Horizontal Layout Group** | 水平一行 |
| **Vertical Layout Group** | 垂直一列 |
| **Grid Layout Group** | **网格（二维，行列）** |

### Grid 的三个不同点（这就是题目问的）
1. **二维**排列，要指定 `Cell Size`（格子大小）和 `Constraint`（约束行数还是列数）
2. **子物体尺寸由 Grid 强制指定**，不看子物体自己的 preferred size
3. 而 Horizontal / Vertical 会**参考子物体的 preferred size** 来排布

三者通常配合 **Layout Element**（指定 preferred/min 尺寸）和 **Content Size Fitter**（让父容器自适应内容）一起用。

## 4.4 Mask 与模板测试 ★★★

### 一句话结论
**Mask 用模板测试（Stencil Test），支持任意形状但打断合批；RectMask2D 用 CPU 算矩形裁剪，只支持矩形但不打断合批。**

| | **Mask** | **RectMask2D** |
|---|---|---|
| 原理 | **模板测试（Stencil Test）** | **CPU 计算矩形裁剪区**，通过 shader 的 `_ClipRect` 丢弃区域外像素 |
| 支持形状 | **任意**（用一张 Sprite 决定形状） | **只能矩形** |
| 性能 | **打断合批**，产生额外 DrawCall | **不打断合批**，性能更好 |
| 适用 | 圆形头像、异形遮罩 | 列表、滚动视图 |

### 关键：模板测试 ≠ 深度测试

| | 深度测试 ZTest | **模板测试 Stencil Test** |
|---|---|---|
| 缓冲区 | 深度缓冲（每像素存深度值） | **模板缓冲（每像素存 8 位整数）** |
| 作用 | 决定**谁遮挡谁**（前后关系） | 决定**某个像素能不能被画** |
| 用途 | 3D 遮挡剔除 | **遮罩、描边、传送门、UI 裁剪** |

> ⚠️ 面经里那位候选人就是把**模板测试说成了深度测试**，面试官引导两次都没反应过来。**这两个别搞混。**

### Mask 用模板测试的工作过程
1. 遮罩图片先渲染，往模板缓冲写入一个参考值（比如 1）
2. 子物体渲染时设置"**只在模板值等于 1 的像素上绘制**"
3. 于是子物体只在遮罩形状内显示，超出部分被丢弃

**为什么 Mask 会打断合批**：它需要额外的材质和渲染步骤来写模板缓冲，破坏了 UGUI 的合批条件。

## 4.5 场景题：方图显示成圆形头像 ★★★

### 三种方案，按优劣排

**方案一：美术直接出圆形图（带 alpha 透明）**
- 最简单，零代码
- ❌ 边缘容易有锯齿；每个头像都要单独出图

**方案二：圆形 Sprite + `Mask` 组件**
- 放一个圆形 Image 挂 `Mask`，头像作为它的子物体，用**模板测试**裁剪
- ❌ **打断合批**，多一个 DrawCall

**方案三：自定义 Shader（最优）**
- 在片元着色器里算 UV 到中心的距离，超出半径直接 `clip()` 丢弃
- 还能顺手做**边缘抗锯齿**（按距离插值 alpha）
- ✅ **不打断合批，性能最好**，可复用到所有头像

### 必须主动说出来的一句
> "**`RectMask2D` 做不了这个**，它只能裁矩形，圆形必须用 `Mask` 或者自定义 Shader。"

这句话是这道题的**得分点** —— 它在考你知不知道两种 Mask 的边界。
